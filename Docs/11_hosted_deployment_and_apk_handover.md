## Deploy in order

1. Grant the connected GitHub account write access, or reconnect an account with write access. Push `feature/india-grocery-platform`; do not replace or force-push `main`. Enable the Render, Neon and Vercel integrations. Optional API token requirements have been saved in the cloud environment draft for secure configuration; saving that draft alone does not activate the tokens or deploy anything.
2. Create an owned Neon project/database, preferably near the API region. Keep the direct and pooled PostgreSQL connection strings private. Set TLS using Neon's connection settings. Use the pooled connection as Render `DATABASE_URL` (a small `connection_limit`, e.g. 5, is appropriate for this single process); use the direct connection as `MIGRATION_DATABASE_URL`. Do not copy local development data or credentials into the hosted database by default.
3. Import the repository in Render and apply the root `render.yaml` after reviewing its plan. It specifies one Starter instance and a persistent 1 GB upload disk: these are paid resources. Do not apply it as a purported free plan. Configure the actual Neon URLs, generated unique JWT/admin secrets, stable payout-encryption key, actual Vercel admin HTTPS origin, owned Google client ID and real Razorpay TEST credentials/webhook secret. The pre-deploy command runs the safe baseline/forward-migration wrapper using the direct connection. Startup derives `PUBLIC_BASE_URL` from Render's actual `RENDER_EXTERNAL_URL`. Production authentication/payment validation remains enabled.
4. Configure Firebase through a Render secret file (`FIREBASE_KEY_PATH`) or backend-only `FIREBASE_SERVICE_ACCOUNT` JSON. A missing sender defers push intents; it is not verified delivery. Register Razorpay's TEST webhook at the deployed backend `/api/payments/webhook`. Do not enable live payments for a personal test.
5. Obtain the actual Render HTTPS origin, then run `GROZO_BACKEND_ORIGIN=https://YOUR-ACTUAL-API-ORIGIN node scripts/configure_hosted_admin.mjs` from the repository root. It configures exact HTTPS/WSS CSP origins and removes the old upstream API routing. Commit that public configuration. Import `web/super_admin` as the Vercel project root, enable inclusion of source files outside the root directory (shared `branding/brand.json` is required), choose Vite/Node 24, output `dist`, and set **both** `VITE_API_BASE_URL` and `VITE_SOCKET_URL` to the backend **origin without `/api`**. They are public client settings, never secrets. Configure any licensed map tile settings separately.
6. Set Render `ADMIN_URL` to the actual Vercel production origin. Use one stable production URL; arbitrary Vercel preview URLs are deliberately not allowed by backend CORS. Redeploy as needed, then check `/health`, database-backed `/ready`, admin login, authenticated catalog/coverage reads, an actual browser request and Socket.io connection. Check product uploads survive a restart and run the authorized gateway TEST/device checks. Never mark the deployment live from a build result alone.

## Reliable APK downloads

`Android phone previews` in GitHub Actions builds one role per job, embeds the actual deployed HTTPS API/socket URLs, and uploads each APK plus installation notes and SHA-256 checksum as a GitHub Actions artifact. Default architecture is arm64; choose `android-arm` for a 32-bit phone. These split profile builds avoid the large universal debug APK. Firebase can be deliberately disabled for a UI preview, or supplied through matching `GROZO_FIREBASE_CUSTOMER_JSON`, `GROZO_FIREBASE_VENDOR_JSON` and `GROZO_FIREBASE_DRIVER_JSON` client-config secrets. Customer Google login still needs owned OAuth client IDs and debug signing fingerprints. No backend service-account key belongs in these artifacts.

For a feature-branch build, set the repository variable `GROZO_BACKEND_ORIGIN` to the verified backend origin and `GOOGLE_SERVER_CLIENT_ID` to the owned web OAuth client ID, then push a change to one of the workflow's watched app/package/branding/build files on `feature/india-grocery-platform`. The push job deliberately skips when the backend variable is absent; a skipped job does not provide APKs. Set `GROZO_PREVIEW_FIREBASE_ENABLED=true` only after supplying all three owned client-config secrets.

GitHub discovers manually dispatched workflows on the default branch. After review, merge the workflow into the default branch through the normal repository process, then choose `feature/india-grocery-platform` as the run ref if appropriate. Do not assume an unmerged feature-only workflow can be manually dispatched from the Actions UI. Alternatively run `scripts/build_android_preview.sh customer` (and vendor/driver) locally with the same environment and upload the resulting files to an authorized GitHub release using working API credentials.

Once a workflow run succeeds, open **GitHub → repository → Actions → Android phone previews → successful run → Artifacts** while signed into an account with repository access. Download each ZIP, extract it, transfer the `.apk` to the phone and open it. Permit installation from that specific browser/file manager when Android asks. Compare `SHA256SUMS.txt` if verifying the transfer. A signing conflict requires a build signed with the existing key or uninstalling the earlier preview (which removes its local data). Development-signed profile previews are not Play Store releases.

A successful run's artifact URL or an authorized release asset URL is the handover link. Do not replace it with another `/workspace/...` path or claim an unpublished local file can be downloaded. If downloads expire after the 14-day artifact retention period, create a new verified run or publish an authorized release asset.

## What must not be bypassed

Do not run a public deployment with test-only authentication, simulated payments, a copied local admin password, wildcard CORS, ephemeral product-photo storage or an emulator-only API address. Release APKs continue to require owned signing keys, matching Firebase clients and real HTTPS endpoints. The existing `scripts/build_mobile_apks.sh` remains the signed-release path.
