# Add demo products to the existing staging database

The hosted Neon database has **not been modified from this workspace**. No Render/Neon connector tools or hosted database connection are available in this session. The operator must apply this reviewed SQL to the isolated staging database. It creates no Clerk identities, login credentials or admin access; existing users and roles are preserved.

1. Open Neon → your Grozo staging project → **SQL Editor**. Select the same branch/database used by Render's DATABASE_URL. Do not select a database containing live production commerce.
2. Open [seed-hosted-catalog.sql](seed-hosted-catalog.sql), copy the entire file, paste into the SQL Editor and click **Run**.
3. The result should list **Grozo Demo Market One · Simulated** and **Grozo Demo Market Two · Simulated**, each with **12 products**.
4. In the customer app, edit the delivery address and select **Bengaluru · Demo (simulated)**, then save/select it. Use the Town Hall simulation coordinates and PIN below. Another city merely named Bengaluru has a different database ID and will not show these stores.
5. Refresh Home. This is a database update; no additional APK or backend deployment is needed to use it. The admin website can show these rows after administrator provisioning.

## Why the earlier seed can return no stores

The app requests `/api/v1/vendors/nearby?marketplace=1&addressId=...`. This requires a non-deleted vendor owner and an active primary store category, in addition to approval/opening status and serviceability. The earlier SQL created unowned stores with no primary store category. Its historical verification used `/api/vendors`, so it did not catch this incompatibility. The corrected seed supplies both business associations and is tested through the exact authenticated customer route. No discovery/authorization filters were removed.

The dataset covers Bengaluru, Karnataka: a simulated 8 km central-city zone, two published public map anchors, eight grocery categories and 24 product packs. Eleven products per store start in stock; tomatoes deliberately show sold out. Prices are in rupees with integer paise MRP values. Initial positive stock movements are recorded. Public ratings start at zero. Seeded products use a zero flat commission override without changing global pricing settings.

Products include milk, bananas, flour, eggs, rice, bread, oil, biscuits, tea, oranges, cleaner and tomatoes. Images are the project's original unbranded AI demo illustrations, pinned to an immutable GitHub source commit; all 12 image downloads were checksum-verified. See [image rights](product-image-licenses.md). The admin CSP allows exactly `https://raw.githubusercontent.com` for images. It does not grant that host script/API permissions.

The SQL runs atomically, uses a distinct `gzhostdemo-blr` namespace and serializes repeats. It inserts missing rows; reruns do not reset existing stock, approval status, opening status or product edits. Conflicting ownership/IDs fail the transaction. Two **new inert vendor-owner business records** supply required ownership: they have no Clerk ID, phone, email, Google subject or password and cannot sign in. The seed upgrades only missing associations on the previous namespaced unowned demo stores. Existing users, identity links, account balances, orders and payment records remain untouched. A random vendor sign-up cannot claim these stores; a verified operator must associate a real approved vendor separately before the vendor app can manage them. Reseeding then refuses that real association rather than overwriting it. No rider assignment or delivery history is fabricated.

For serviceability tests, save an explicitly simulated address under **Bengaluru · Demo (simulated)** at the published Town Hall anchor: latitude `12.96393155`, longitude `77.58425661`, PIN `560002`, house “DEMO Unit C01 (simulated)”, street/locality “Town Hall”, label “Demo address · Simulated”. Do not enter this as a real home address or arrange a physical delivery. The seed does not switch cities for existing customer addresses. The current automated regression also proves an address in another same-named Bengaluru is not reassigned silently and becomes serviceable after the customer explicitly selects the demo city. Payments are not enabled by this SQL.
